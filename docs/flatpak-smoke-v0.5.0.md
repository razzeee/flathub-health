# flatpak-smoke v0.5.0 integration

Baseline: GitHub main `dc8bf88`, v0.4.2 (`779736cabe5288531465ceeec5d6ed5e1c3921d6`). No open consumer PRs when work started. The only intervening release is [v0.5.0](https://github.com/razzeee/flatpak-smoke/releases/tag/v0.5.0), published 2026-10-22 16:45:29 UTC. Inventory checked against the [complete source comparison](https://github.com/razzeee/flatpak-smoke/compare/v0.4.2...v0.5.0), not only release highlights.

## Feature coverage

- **Source and images:** pin release revision `66bbd6723e1f3d5a032441c615e491369fa80093` and both published image digests in `runner.json`. Upstream's timed Docker invocation pulls by digest if needed; retain human-readable release tags in provenance. No consumer-side image resolver or Docker inspection adapter.
- **Reusable dependency repository:** configure Flatpak `languages '*'` before host installation to obtain complete Locale deployments, then call upstream `action/prepare-dependencies.py` to enumerate deployed checksums and atomically export a new snapshot. Both phases receive the same read-only `dependency-repo`; each still gets a private installation/profile. `dependency-inputs.json` records the available set; phase runtime metadata records the selected set. Upstream owns runtime enumeration and export.
- **Dependency limitations:** allow network fallback for backend-specific extensions absent from host preparation (for example KDE Wayland decorations). This is not a complete offline dependency lock or an equivalent-input speed benchmark. Actual selected commits remain authoritative; missing optional extensions can still be skipped. No shared writable installation, cross-job cache, or cache transport is introduced.
- **Published app repository:** replace bundle export with upstream's `repo` + `app-ref` interface. Publish the resolved app commit using one OSTree local-ref command and generate a Flatpak repository summary. Freeze the repository before either phase starts; upstream mounts it read-only and creates private installations. This removes bundle serialization, while retaining the separate upstream dependency snapshot.
- **Web evidence:** expose failure category/reason/message, execution versus cleanup outcomes, per-phase app/runtime/extension provenance, expandable full hashes and raw records, and startup-versus-recipe capture limits. Legacy missing provenance stays explicitly unknown.
- **Wrapper deadlines and cleanup:** use action execution/cleanup budgets of 420/30 seconds, with the CLI's 5-minute budget inside and a 480-second process deadline outside. External cancellation allows 40 seconds for wrapper cleanup. Retain sibling `verify.execution.json` / `screenshots.execution.json` in existing uploads and parsed diagnostics in compact records/reports. A CLI pass with missing/failed wrapper diagnostics or cleanup is not a health pass; specific CLI failures are retained alongside cleanup evidence.
- **Failure categories:** preserve optional/null/future `failure.category`. Known infrastructure categories override app/recipe attribution; `expectation` maps to recipe failure without claiming the app is broken. A bare unclassified `screenshot_failed` is conservatively infrastructure/unassessed, not automatically a recipe regression. Existing specific app reasons retain their phase attribution. Unknown categories do not imply app failure.
- **Seeded input provenance:** retain YAML-only `content_hash` and nullable/versioned `input_digest`; report both and include fixture-inclusive digest in history comparisons. Old artifacts remain readable; missing digests are explicitly unknown, never proof of unchanged fixtures.
- **VLC focus and first-run modals:** inherit bounded exact-window focus readiness and transient-modal ancestry fixes. Explicitly suppress VLC's privacy prompt and metadata-network access in the recipe; repeat the five-second video during capture, keeping the media filename OCR condition, with no `--play-and-exit`. No focus/window-ownership checks are relaxed.
- **Publication guards:** inherit nonblank/pointer-excluding capture validation (already introduced in v0.4.2) and stability fixes. Existing consumer gallery tests publish only declared captures, never diagnostic candidates. Pixel variation or a visible window does not prove application readiness.
- **Upstream-only regression changes:** nested-modal helper tests and asynchronous exit fixture attribution are upstream test coverage; no matching consumer implementation is needed. Their runtime fixes arrive through the pinned images.

## Readiness boundaries

GIMP's editor recipe and welcome suppression already landed in #42; retain its English title plus Tools/Filters assertions. Its startup phase can still pass on a plug-in splash. Firefox remains explicitly startup-only, with a first-run welcome capture, not a verified web page. Neither app gains a new readiness claim from this release. VLC media success requires hosted content evidence; a filename/title alone is insufficient to establish visible playback.

## Validation

Local checks and hosted run/screenshot evidence are recorded in the PR and appended here when available. Hosted branch dispatches do not publish production Pages. All app/recipe/infrastructure failures remain visible in reports even when other phases succeed.

## Consumer responsibility audit

The follow-up to #45 removes the local Docker preflight, image pull/inspection/digest-resolution adapter, invocation-path checks duplicated by the action, and screenshot existence/containment checks duplicated by upstream publication and the website's artifact boundary. It also replaces per-runtime checksum/origin queries and full OSTree pulls with Flatpak's supported complete-locale configuration plus the upstream exporter. Tests for those removed implementations are deleted; health-level phase independence remains tested.

Keep the process adapter: it also bounds host installation/export, streams logs, and cancels host subprocess groups. Upstream explicitly recommends an outer process deadline; its wrapper alone cannot clean up host preparation. Keep result/record schemas for old artifacts, missing evidence, catalog identity and website ingestion. Keep wrapper cleanup interpretation: upstream deliberately preserves CLI exit status even when cleanup fails. Keep classification, history and app-specific recipes: upstream supplies observations, not this service's health policy. No local focus retries, input hashing, pixel heuristics, profile/cache sharing or container lifecycle implementation is needed.

Production-code accounting (`git diff --numstat`, including comments/blank lines): backend TypeScript is **96 lines smaller** than merged #45 (`da5329b`), and **40 lines larger** across the complete upgrade from `dc8bf88`; orchestration contributes just **+1** of those 40 lines. The subsequently requested web presentation adds **247 lines** (184 TSX and 63 CSS), giving **+151 production lines** versus #45 or **+287** across the full upgrade. This growth presents health evidence to readers rather than reimplementing upstream mechanics. Tests and documentation are excluded.

Local validation of the web/repository follow-up: 57 tests, TypeScript checking and production build; real hosted report inspected at desktop and 390px mobile width, including failure explanations and expandable provenance. Hosted validation of repository inputs is required separately; local command-contract tests do not prove Flatpak installation success.
